# Engineering Notes

## 1. Product-first Architecture

기술을 먼저 정한 뒤 기능을 끼워 맞추기보다 사용자 흐름을 기준으로 경계를 정했습니다.

- 지원자는 빠르게 정보를 확인하고 지원해야 합니다.
- 응시자는 제한 시간 안에 문제에만 집중해야 합니다.
- 관리자는 많은 정보를 비교하고 결정해야 합니다.
- 신입사원은 매일 반복적으로 학습하고 질문해야 합니다.

이 차이를 반영해 프론트엔드는 네 개로 분리하고, 데이터 규칙은 하나의 NestJS API에 모았습니다.

## 2. Why NestJS and TypeORM?

채용, 시험, 평가, 온보딩처럼 상태와 권한이 많은 도메인에서는 모듈 경계가 중요합니다. NestJS의 모듈과 의존성 주입을 사용해 기능을 나누고, TypeORM 엔티티와 Repository로 데이터 접근을 분리했습니다.

복잡한 관리자 조회와 상태 변경은 SQL의 표현력이 더 적합해 Repository 안에서 명시적인 SQL과 트랜잭션을 사용했습니다. 단순 CRUD만 ORM에 의존하지 않고 두 방식을 목적에 따라 혼합했습니다.

## 3. Why PostgreSQL?

- 지원 전형과 시험 세션의 상태 무결성을 보장할 수 있습니다.
- JSONB로 지원서와 AI 결과의 유연한 구조를 저장할 수 있습니다.
- 트랜잭션과 행 잠금으로 동시에 발생하는 관리자 결정을 처리할 수 있습니다.
- 향후 `pgvector`를 도입하면 별도 벡터 DB 없이 RAG를 확장할 수 있습니다.

## 4. AI as an Assistant, Not a Decision Maker

채용은 결과에 대한 설명 책임이 필요한 영역입니다. 따라서 Relay는 AI가 합격 여부를 직접 결정하는 대신 다음 정보를 제공합니다.

- 원문 요약
- 직무 요건과의 대응 근거
- 확인된 강점
- 정보가 부족하거나 모순된 항목
- 다음 면접에서 물어볼 질문

관리자는 원문을 확인하고 최종 결정을 내립니다. 기술 문제의 평가 기준도 AI 초안 이후 사람의 승인을 거칩니다.

## 5. Important Implementation Decisions

### Preserve assessment history

AI 결과를 덮어쓰지 않고 분석 유형과 리비전으로 저장합니다. 모델이나 프롬프트가 바뀌어도 이전 판단 근거를 추적할 수 있습니다.

### Snapshot exam inputs

시험 질문과 답변은 제출 당시 상태를 스냅샷으로 보존합니다. 문제은행이 나중에 바뀌어도 당시 응시 내용을 재현할 수 있습니다.

### Separate secrets from source

DB 연결 문자열, 암호화 키, JWT 비밀키, AI API 키는 환경변수로 분리합니다. 포트폴리오 저장소에는 예시 파일만 포함하고 실제 값은 커밋하지 않습니다.

### Bridge two admin experiences

채용 관리자로 로그인한 사용자가 온보딩 관리자 화면으로 전환할 때 다시 로그인하지 않도록, 검증된 채용 세션을 온보딩 JWT로 교환하는 SSO 브리지를 구현했습니다.

## 6. Challenges and Learnings

### Different UIs, one domain flow

네 개의 앱이 동일한 디자인 언어를 유지하면서도 각 사용자의 작업 밀도에 맞는 화면을 제공해야 했습니다. 브랜드 색상과 타이포그래피는 통일하고 레이아웃은 역할별로 다르게 설계했습니다.

### Making small-model output usable

로컬 모델은 JSON 형식을 요청해도 코드펜스를 포함하거나 일부 필드를 누락할 수 있습니다. 코드펜스 제거, 스키마 파싱, 필수 필드 검증, 명확한 오류 변환을 추가해 UI와 DB가 불완전한 응답을 그대로 소비하지 않도록 했습니다.

### Reconciling MVP and production design

MVP는 전체 흐름을 빠르게 검증해야 하지만 채용 데이터는 민감합니다. PASS 우회와 고정된 데모 지원자 같은 시연 경로를 명시적으로 격리하고, 운영 전 교체해야 할 지점을 문서화했습니다.

## 7. Current MVP Boundaries

| Area | Current MVP | Production next step |
|---|---|---|
| PASS | 연동 경계 + 로컬 우회 | 운영 키, 콜백 검증, 장애 대응 |
| Resume files | 메타데이터 중심 | Object Storage, 백신 검사, 서명 URL |
| Exam identity | 데모 지원자 연결 | 인증된 지원서–시험 세션 매핑 |
| AI analysis | 구조화 분석 및 저장 | 골든셋 평가, 편향 점검, 비용·지연 모니터링 |
| RAG | 임베딩 또는 전체 문서 폴백 | pgvector, 재색인, 검색 품질 평가 |
| Authorization | 역할 기반 흐름 | 전체 관리자 API 가드·세부 권한 강화 |
| Audit | 데이터 모델과 경계 | 중요 액션 기록 및 관리자 조회 UI |

## 8. Roadmap

1. 지원서 첨부파일을 Object Storage에 실제 업로드
2. 인증된 지원자와 시험 세션을 동적으로 연결
3. 시험 중 AI 대화 로그와 답안 리비전 저장
4. 서류·시험 분석을 결합한 최종 리포트
5. 최종 합격 데이터를 개인별 온보딩 플랜 초기값으로 자동 연결
6. 관리자 판단과 AI 분석의 차이를 기록하는 평가 데이터셋 구축
7. pgvector 기반 문서 검색과 RAG 평가 자동화
8. 감사 로그와 개인정보 보존·파기 정책 운영화

## 9. Verification Snapshot

MVP 점검 기준으로 다음 항목을 검증했습니다.

- 네 개의 프론트엔드 린트와 프로덕션 빌드
- 백엔드 타입 검사, ESLint, NestJS 빌드
- Jest 테스트 5개 스위트, 11개 테스트
- TypeORM 마이그레이션 17개 적용 상태
- 주요 지원자·관리자·시험·온보딩 API 응답
- 주요 브라우저 사용자 흐름과 콘솔 오류

정량적인 채용 시간 절감률이나 AI 정확도는 아직 측정하지 않았기 때문에 포트폴리오에서 성과 수치로 주장하지 않습니다.
